# Security

Report a vulnerability privately with GitHub's private vulnerability reporting (the repository's Security tab, Report a vulnerability). Please do not open a public issue for it.

## Design

The helper holds Accessibility (and Screen Recording, when the user turns it on for screenshots, and System Audio Recording, when the user turns it on for `record_audio`), so it also holds the app list: agents may use an app only when the user put it on the list or turned on Allow every app, and nothing asks during a task. The list keeps agents from using other apps through Backstage by mistake; it does not stop an agent that can run shell commands (see below). The `backstage` command only checks arguments and forwards requests; it holds no permission itself. A process that talks to the socket directly meets the same gate for using apps. Over the socket it can remove apps from the list, which only narrows access, but adding one only asks: the request waits on the Apps tab until the user adds it there, since the socket cannot tell an agent from the user running the same command. Such a request, like one for Screen Recording or System Audio Recording, brings the Backstage window forward once.

The socket offers a few requests that touch no app and pass no list check. Any client can quit the helper (`quit`), which ends the requests of every session, and can turn off Open at login and the menu bar item and quit it (`prepare_uninstall`, which `backstage uninstall` uses). While Accessibility is missing, any client can make macOS show its Accessibility prompt (`request_permissions`, which `setup` uses); the user still decides in System Settings.

- Backstage keeps its files in three `0700` directories, at the XDG defaults: the app list and the settings in `~/.config/backstage`, the signing keychain in `~/.local/share/backstage`, and the activity log and the socket in `~/.local/state/backstage`. Files with content are `0600`. The `XDG_*` variables are not read, because the app also starts from launchd without the shell's environment. Open at login is a macOS login item, and the permissions are in macOS's own records.
- Every request that touches an app resolves it, checks it against the list, and checks that the process is still the one resolved.
- List entries are bound to the bundle id and the signer: Apple's own apps by Apple's anchor, so a system update keeps them on the list; other apps by team id, by their signing certificate when they have no team (an app signed with its own certificate stays on the list across its updates), or by code hash when ad hoc signed. An app without a valid signature cannot go on the list. Removing an entry applies to the next request of every session. An app asked for while it ran, and added after it quit or its process id went to another process, is bound to the signature of the bundle at the path it had, when that bundle still has the same bundle id; otherwise adding fails with `app_not_found`. Passwords (with its helpers, such as its menu bar extra), Keychain Access, the macOS processes that show login, authentication and permission prompts (`loginwindow`, `SecurityAgent`, the Local Authentication and permission prompt agents, the user notification center), and Backstage itself are never available. A sign-in or password window inside an allowed app, such as a page in a browser or an account sheet in Mail, belongs to that app and is reachable like the rest of it; only secure field values stay hidden. Neither are other makers' password managers (such as 1Password, Bitwarden, LastPass, Keeper, KeePassXC, Proton Pass and Enpass), authenticators (Yubico Authenticator, Ente Auth) and wallets (such as Ledger Live, Trezor Suite, Sparrow, Electrum and Bitcoin Core), matched by their bundle id families without regard to case, even with Allow every app on; `list_apps` answers `never_available` for such an id also when this Mac does not have the app. The full list is in `Sources/App/Approvals.swift`; an app whose id is not on it is held back only by the user's list.
- Items in the Apple menu (Restart, Shut Down, Log Out, System Settings) and in the Services and Share menus of every app, in the menu bar or a context menu, and the Share button of a toolbar are refused with `not_allowed`, since they act on the whole Mac or hand the app's content to other apps past the list. `list_menu_commands` leaves them out. The check is in `Sources/App/MenuSafety.swift` and covers these routes, alone and as `run_actions` steps:
  - every tool that names an element: `press`, `set_value`, `type_text`, `select_text`, `scroll`, `click_at` with `element`, both ends of `drag`, and the element `record_audio` presses;
  - `run_menu_command`;
  - `press_key` with a shortcut of such an item, a combination with cmd or ctrl: the Apple menu's own, which are fixed (shift+cmd+Q, option+shift+cmd+Q, ctrl+cmd+Q, option+cmd+esc, option+shift+cmd+esc), and those shown for the items of the app's Apple menu, the Services submenu of its app menu, and Services or Share submenus directly under a top-level menu; the rest of the menu bar is not read. When those menus cannot be read within about a second, the key is not sent and the reply is `timeout`;
  - `press_key` with return or space while such an item is selected in an open menu, and `type_text` with text that contains a space while the app shows a menu, since letters select an item by its name and the space confirms it;
  - every click and both ends of every drag, against what lies under the point right before the events are posted, whether the point was given as coordinates or is the center of an element: `click_at`, `drag`, and `press` on an element without an action, which falls back to a click at its center. A part of an item, such as its image or text, counts as the item. When Accessibility cannot tell what lies under the point, as in many custom views and web content, or gives only the window, the click is refused while the app shows a menu or one of its windows at menu level covers the point, and goes on otherwise.

  What the check does not cover:
  - On a locked screen, with Windows while locked on, `press_key` checks shortcuts, but `press_key`, `type_text` and `click_at` cannot check an open menu's selection or what lies under a point, because Accessibility does not reach windows then.
  - A service's shortcut that the app's menu bar shows only once the Services menu has opened is unknown, apart from the Apple menu's fixed list.
  - A Share submenu nested inside another submenu is not searched for shortcuts; its items are still refused when pressed or clicked.
  - Where Accessibility cannot tell what lies under a point and the app shows no menu, a click there is not checked: a Share button drawn in a custom view or web content is not recognized.
  - A Share button outside a toolbar, or labelled other than AppKit's Share, is not recognized.
  - Arrow keys move through an open menu freely; the refusal comes at the key that confirms the item.
- A call with `computer` goes only to a Mac on this Mac's list of other Macs, which only the window adds to: a Mac not on it is refused with `computer_not_approved` before ssh runs, and the request waits in the window, so text an agent reads cannot send it to another Mac on its own. The call then goes through `/usr/bin/ssh` in batch mode, which never asks for a password, so it reaches only Macs the user can already log in to with a key. The name is checked before ssh runs (letters, digits, `.`, `-` and `_`, starting with a letter or digit), so it cannot pass ssh an option, a user or a command, and the command ssh runs there is fixed: that Mac's installed `backstage mcp`. That Mac's helper, app list and settings decide the call; this Mac's list does not apply there and is not consulted. Replies from another Mac are passed on as they come, like any tool output. Whoever can log in to that Mac over SSH can already run its `backstage mcp` directly, so `computer` adds no access the key did not give, and an agent with a shell can run ssh itself; on a Mac you reach over SSH, the app list is what limits it.
- Text recognized in a screenshot (`screenshot` with `text: true`) only describes the image. It never chooses a click, an element or a key and never verifies an action, so text a page or a document draws cannot steer an action through it; an agent that reads it decides for itself, and its clicks pass the same checks as any other.
- `list_windows` shows titles and window states only for apps on the list. For every other app, including those never available, it shows the app's name and bundle id, its access, and where each window is (frame, display, front-to-back order, on screen), and it names the front app. `list_apps` likewise lists every running app with a Dock icon by name and bundle id, with its access.
- The socket bounds a request to 4 MB, the requests waiting on one connection to 64, connections to 64 and remembered sessions to 256, so one client cannot exhaust the helper. Screen Recording and System Audio Recording are asked for only when the user chooses Allow in the window. A request that needs one only leaves an Allow button there, as a request to add an app does; macOS's prompt never shows because a client asked. `record_audio` taps only the sound of the app named, which has to be on the list, and of the processes it started or that sit in its bundle; it never records the microphone or other apps.
- Element numbers belong to one session and one app. A number whose element changed what it is since the agent read it (role, labels, or the value of text, cells and rows) is refused as stale.
- `launch_app` takes app names only, never paths. The files it hands an app on the list must be the user's own reachable files (the same rule as ready operations) or copies Backstage made in its private temporary folders, such as recordings; links are resolved before the check.
- Clicks, drags and keys reach only the allowed app's process, except `click_at` with `foreground: true`, which goes through the system. Right before each press it checks that the window on top at that point belongs to that app, and refuses with `point_covered` otherwise. The check and the click are not one atomic step, so a window that appears in between can still take the click; this is best effort. The Backstage window ignores every pointer event the helper itself posted, so an agent cannot change the list through it.
- `run_operation` runs only operations compiled into the helper, looked up in the allowed app's own catalog. Scripts are fixed; arguments are validated in the helper and reach the short-lived `osascript` child as one JSON value on its standard input, never spliced into script text and never on its command line, so they do not show in the list of processes. System Settings' `get_appearance` and `set_appearance` script System Events, which needs no place on the list of its own: allowing System Settings covers them, with System Events' Automation grant. Allowing Reminders or Calendar also lets agents read and change that data through EventKit while the app is closed. Contacts works the same way. Messages' `list_chats` and `read_chat` from its database also read contact names, only to label chats and senders as Messages does, only while Contacts is on the list and its macOS grant is on, and never prompt for it; removing Contacts from the list stops them. Shortcuts is far-reaching, because a shortcut can run shell scripts, so the list warns about it. Mail operations never send mail. Messages `send` does, in the user's name, and cannot be undone. Finder, Pages and Numbers operations reach only files in the home folder (not the folder itself) and on other volumes (`/Volumes`), including documents Pages or Numbers already have open; a link is checked by where it leads when an operation opens it; Finder moves to the Trash rather than deleting, and exports never replace a file. WhatsApp operations, and Messages `list_chats`, `read_chat` and `save_attachment` once the Messages history grant is on, read chats and attachments from the apps' databases; messages from others can carry one-time codes, reset links and text written to steer an agent, so allow these only for agents you trust with them. They need Full Disk Access, which lets the helper read any file, so every operation that takes a path refuses the home folder's Library apart from iCloud Drive and cloud storage, whatever letter case the path gives it, and on other volumes a `Users/<name>/Library` folder and Time Machine backups; a path inside a folder macOS keeps from Backstage, such as Documents before the user allows it, answers `permission_missing`, naming the folder and System Settings > Privacy & Security > Files and Folders; and `save_media` refuses a stored path outside WhatsApp's folder. Photos operations find and copy out photos and videos through PhotoKit, whose macOS grant also allows changes, though no operation makes any. The macOS grants for Automation, Reminders, Calendars, Contacts, Photos and Full Disk Access belong to Backstage and do not replace the list.
- Secure field values are never returned.
- A locked screen does not pause allowed apps. While it is locked, agents can still run ready operations and the menu commands of apps on the list, but cannot read their windows. Backstage never unlocks the Mac, keeps no password and does not wake the displays. With **Windows while locked** on (off by default, on the Setup tab), agents can also capture the windows of allowed apps and click and type in them by position while the screen is locked, through private window server calls that keep working after macOS hides windows from Accessibility and ScreenCaptureKit. Such actions are never verified, and the user cannot watch them; turning the switch on or off is logged. See [docs/locked-screen.md](docs/locked-screen.md).
- Private macOS calls are looked up at run time and fall back to public ones, or fail with a clear error, when missing: SkyLight's `SLEventPostToPid`, `CGEventSetWindowLocation` and `SLPSPostEventRecordTo` for background input, `SLSHWCaptureWindowList` and `SLSMainConnectionID` for capture while locked, and `_AXUIElementGetWindow` for window numbers. Backstage uses them only for what its grants already cover: input needs Accessibility, and the helper captures a window only with Screen Recording granted.
- The first use of each app in each session and every change to the list are logged to `decisions.jsonl` (`0600`) with the time, client and app, never content. The client is the name its MCP client reports, kept to one line without control characters and at most 40 characters. A client cannot name itself as the window or the command line (`settings`, `command_line`, or a name that reads as You or Command line, as the Activity tab shows those two); such a name is logged as none. Otherwise a client can name itself anything. Past 200 KB the log keeps the newest records that fit in 100 KB, at most a thousand; a record over 4 KB is not written, and longer or unreadable lines are skipped when the log is read. The list is in `approvals.json` (`0600`). Both are a local history and setting, not tamper-proof.

## What it does not protect against

- **A process running as you that can write files.** `approvals.json` has no integrity protection, so such a process can add any app to the list by editing the file, or turn on Allow every app or Windows while locked in `settings.json`; the confirmation in the window covers only requests over the socket. It can also connect to the socket: the helper does not check who is on the other end, because such a process could run the real server itself, and the list in the helper applies to it like to any agent. It can also control apps without Backstage at all, through AppleScript and other tools. Backstage's instructions to MCP clients ask agents to respect the list by every route, not only its tools, and never to change the list themselves. A cooperative agent follows that; nothing enforces it. If an agent has unrestricted shell access, the list protects against mistakes and relies on the agent's cooperation, not against an agent that ignores it.
- **What an allowed app can do.** Allowing an app covers everything in it, including its own access to files, accounts and commands. That is why far-reaching apps carry a warning on the list.
- **Page or document content.** An agent reading a window can receive instructions planted there. Allow only the apps your tasks need.

## Signing

`setup` signs the installed app with a self-signed certificate, so macOS keeps its permissions across updates without a paid Developer ID. The private key lies in `signing.keychain-db` in `~/.local/share/backstage`, a `0700` directory, with an empty password. **A process running as you can use that key to sign its own code as this app, and then inherit Accessibility and Screen Recording, the Automation, Reminders, Calendars, Contacts and Photos grants, and Full Disk Access when it is on, which reads every file.** An agent with unrestricted shell access can do this. Nothing else signs or replaces the app on its own: only an explicit `setup` does, and the installed app ignores `--home`, which only a bare test build outside a bundle honors. Such a build, which holds no permissions, adds an app asked for over the socket at once only with `--home`; without it, it uses the user's files and leaves the request for the user, like the installed app. Closing the key exposure needs an app signed with a Developer ID whose key is not kept on this Mac.
