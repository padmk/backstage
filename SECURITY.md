# Security

Report a vulnerability privately with GitHub's private vulnerability reporting (the repository's Security tab, Report a vulnerability). Please do not open a public issue for it.

## Design

The helper holds Accessibility (and Screen Recording, when the user turns it on for screenshots), so it also holds the app list: agents may use an app only when the user put it on the list or turned on Allow every app, and nothing asks during a task. The list keeps agents from using other apps through Backstage by mistake; it does not stop an agent that can run shell commands (see below). The `backstage` command only checks arguments and forwards requests; it holds no permission itself. A process that talks to the socket directly meets the same gate for using apps. Over the socket it can remove apps from the list, which only narrows access, but adding one only asks: the request waits on the Apps tab until the user adds it there, since the socket cannot tell an agent from the user running the same command.

- Backstage keeps its files in three `0700` directories, at the XDG defaults: the app list and the settings in `~/.config/backstage`, the signing keychain in `~/.local/share/backstage`, and the activity log and the socket in `~/.local/state/backstage`. Files with content are `0600`. The `XDG_*` variables are not read, because the app also starts from launchd without the shell's environment. Open at login is a macOS login item, and the permissions are in macOS's own records.
- Every request that touches an app resolves it, checks it against the list, and checks that the process is still the one resolved.
- List entries are bound to the bundle id and the signer: Apple's own apps by Apple's anchor, so a system update keeps them on the list; other apps by team id, by their signing certificate when they have no team (an app signed with its own certificate stays on the list across its updates), or by code hash when ad hoc signed. An app without a valid signature cannot go on the list. Removing an entry applies to the next request of every session. Passwords (with its helpers, such as its menu bar extra), Keychain Access, login, authentication and permission prompt windows, and Backstage itself are never available.
- Items in the Apple menu (Restart, Shut Down, Log Out, System Settings) and the Services and Share menus of every app are refused on every route (`press`, `run_actions`, `run_menu_command`), since they act on the whole Mac or hand the app's content to other apps past the list. `list_menu_commands` leaves them out. `list_windows` shows titles only for apps on the list; other apps' windows show only where they are.
- The socket bounds a request to 4 MB, the requests waiting on one connection to 64, connections to 64 and remembered sessions to 256, so one client cannot exhaust the helper. Screen Recording is asked for only from the Setup tab, never over the socket.
- Element numbers belong to one session and one app. A number whose element changed what it is since the agent read it (role, labels, or the value of text, cells and rows) is refused as stale.
- `launch_app` takes names only, never paths.
- Clicks, drags and keys reach only the allowed app's process, except `click_at` with `foreground: true`, which goes through the system. Right before each press it checks that the window on top at that point belongs to that app, and refuses with `point_covered` otherwise. The check and the click are not one atomic step, so a window that appears in between can still take the click; this is best effort. The Backstage window ignores every pointer event the helper itself posted, so an agent cannot change the list through it.
- `run_operation` runs only operations compiled into the helper, looked up in the allowed app's own catalog. Scripts are fixed; arguments are validated in the helper and passed as data after `--`, never spliced into script text. Allowing Reminders or Calendar also lets agents read and change that data through EventKit while the app is closed. Contacts works the same way. Shortcuts is far-reaching, because a shortcut can run shell scripts, so the list warns about it. Mail operations never send mail. Messages `send` does, in the user's name, and cannot be undone. Finder, Pages and Numbers operations reach only files in the home folder (not the folder itself) and on external volumes, including documents Pages or Numbers already have open; a link is checked by where it leads when an operation opens it; Finder moves to the Trash rather than deleting, and exports never replace a file. WhatsApp operations read its chats and attachments from its database; they need Full Disk Access, which lets the helper read any file, so every operation that takes a path refuses the home folder's Library apart from iCloud Drive and cloud storage, and `save_media` refuses a stored path outside WhatsApp's folder. The macOS grants for Automation, Reminders, Calendars, Contacts and Full Disk Access belong to Backstage and do not replace the list.
- Secure field values are never returned.
- A locked screen does not pause allowed apps. While it is locked, agents can still run ready operations and the menu commands of apps on the list, but cannot read their windows. Backstage never unlocks the Mac, keeps no password and does not wake the displays. With **Windows while locked** on (off by default, on the Setup tab), agents can also capture the windows of allowed apps and click and type in them by position while the screen is locked, through private window server calls that keep working after macOS hides windows from Accessibility and ScreenCaptureKit. Such actions are never verified, and the user cannot watch them; turning the switch on or off is logged. See [docs/locked-screen.md](docs/locked-screen.md).
- Private macOS calls are looked up at run time and fall back to public ones, or fail with a clear error, when missing: SkyLight's `SLEventPostToPid`, `CGEventSetWindowLocation` and `SLPSPostEventRecordTo` for background input, `SLSHWCaptureWindowList` and `SLSMainConnectionID` for capture while locked, and `_AXUIElementGetWindow` for window numbers. Backstage uses them only for what its grants already cover: input needs Accessibility, and the helper captures a window only with Screen Recording granted.
- The first use of each app in each session and every change to the list are logged to `decisions.jsonl` (`0600`) with the time, client and app, never content. Past 200 KB, about two thousand records, it keeps the newest thousand. The list is in `approvals.json` (`0600`). Both are a local history and setting, not tamper-proof.

## What it does not protect against

- **A process running as you that can write files.** `approvals.json` has no integrity protection, so such a process can add any app to the list by editing the file, or turn on Allow every app or Windows while locked in the helper's defaults; the confirmation in the window covers only requests over the socket. It can also connect to the socket: the helper does not check who is on the other end, because such a process could run the real server itself, and the list in the helper applies to it like to any agent. It can also control apps without Backstage at all, through AppleScript and other tools. Backstage's instructions to MCP clients ask agents to respect the list by every route, not only its tools, and never to change the list themselves. A cooperative agent follows that; nothing enforces it. If an agent has unrestricted shell access, the list protects against mistakes and relies on the agent's cooperation, not against an agent that ignores it.
- **What an allowed app can do.** Allowing an app covers everything in it, including its own access to files, accounts and commands. That is why far-reaching apps carry a warning on the list.
- **Page or document content.** An agent reading a window can receive instructions planted there. Allow only the apps your tasks need.

## Signing

`setup` signs the installed app with a self-signed certificate, so macOS keeps its permissions across updates without a paid Developer ID. The private key lies in `signing.keychain-db` in `~/.local/share/backstage`, a `0700` directory, with an empty password. **A process running as you can use that key to sign its own code as this app, and then inherit Accessibility and Screen Recording, the Automation, Reminders, Calendars and Contacts grants, and Full Disk Access when it is on, which reads every file.** An agent with unrestricted shell access can do this. Nothing else signs or replaces the app on its own: only an explicit `setup` does, and the installed app ignores `--home`, which only a bare test build outside a bundle honors. Closing the key exposure needs an app signed with a Developer ID whose key is not kept on this Mac.
